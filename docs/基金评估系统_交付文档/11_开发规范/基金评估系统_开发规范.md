# 基金评估与模拟交易系统 · 开发规范（Dev Standards）

> **版本**：v1.0 ｜ **适用范围**：本项目全部研发活动（后端 / 前端 / 数据 / 算法 / 文档 / 发布）
> **目的**：在开发阶段以"规范前置约束"保障代码质量、规范协作流程、提高交付物质量与可维护性。
> **性质**：强制性约束（红线项违反须拦截合并/发布）；与既有《技术规格》《详细设计》《技术方案(TP-01~06)》《模块复杂度评估》共同构成开发依据。

## 1. 代码规范

### 1.1 语言与运行时
- **运行时**：Python **3.11+**（锁定小版本，禁止在 3.11 下使用已弃用语法）。
- **类型注解**：所有模块级函数、方法、公共 API 入口**强制类型注解**；启用 `mypy --strict` 作为 CI 门禁（新增代码 `Any` 需注明原因）。
- **禁止项**：禁止 `eval` / `exec` / `pickle` 反序列化不可信数据 / `os.system` 拼接命令；禁止裸 `except:`（见 §8）。
- **入口单一**：应用仅 `api/`、`workers/` 提供进程入口；算法/领域逻辑置于 `domain/`，不依赖 Web 框架（便于单测与批算复用，见 ADR-002）。

### 1.2 命名规范
| 对象 | 约定 | 示例 |
|------|------|------|
| 模块 / 包 | `snake_case`，全小写，避免缩写歧义 | `score_engine.py`、`brinson.py` |
| 类 / 异常 | `PascalCase` | `ScoreService`、`InvalidWeightError` |
| 函数 / 变量 | `snake_case` | `build_percentile_tables` |
| 常量 / 枚举 | `UPPER_SNAKE_CASE` | `SCORE_WEIGHTS`、`REDEEM_FEE_BY_HOLD` |
| 布尔变量 | 以 `is_` / `has_` / `can_` 开头 | `is_market_closed` |

- 命名**表达意图而非类型**：避免 `data2`、`tmp_list`；用 `portfolio_weights`、`nav_series`。
- 不以下划线前缀模拟私有（`_helper` 仅表"模块内使用"，非强制私有）。

### 1.3 格式与静态检查（门禁）
- **格式化**：`black`（行宽 100）、`isort`（profile=black）。提交前自动格式化，CI 不允许未格式化差异。
- **Lint**：`ruff`（合并 flake8 + isort + 部分 pylint 规则），规则以 `pyproject.toml`/`ruff.toml` 集中管理；`E/F` 类（错误/危险）**零容忍**，`W` 类需评审豁免。
- **类型**：`mypy --strict`（渐进式，新模块全开）。
- **复杂度**：单函数圈复杂度 **≤ 10**；超出须拆函数或加 `# complexity-acknowledged` 说明并经评审。
- **pre-commit**：仓库配置 `.pre-commit-config.yaml`，本地提交自动跑 black/isort/ruff/mypy；CI 复核，任一失败**阻断合并**。

### 1.4 注释与文档字符串
- **docstring**：公共函数/类使用 **Google 风格** docstring（Args / Returns / Raises），示例：
  ```python
  def brinson_attribution(code: str) -> dict:
      """对混合/股票型基金做 Brinson 三向归因。

      Args:
          code: 基金代码（带后缀，如 000001.OF）。
      Returns:
          含 allocation/selection/interaction 与 active_return 的字典；
          持仓缺失时 unavailable=True。
      Raises:
          InvalidWeightError: 披露权重和显著>1 时。
      """
  ```
- **注释解释 why 而非 what**：不写 `i += 1  # i加1`；写 `i += 1  # 跳过停牌日，避免未来函数`。
- **算法口径**：涉及金融算法须注明依据（如 `# 见 TP-01 §3.3，几何链接 Carino 平滑`），禁止"魔法数字"无出处。
- **TODO/FIXME**：`TODO(owner): 描述` 格式，并挂 Issue；禁止无 owner 的 `TODO`。

### 1.5 函数与类设计
- **单一职责**：一个函数只做一件事；超过 40 行考虑拆分。
- **参数数量**：≤ 5；超过用 `dataclass` / `TypedDict` 聚合（如 `DcaParams`）。
- **纯函数优先**：评分/归因/回测等计算应可纯函数化（输入→输出，无隐式全局状态），便于 §8 测试与多进程复用（见 ADR-002 唯一权威源）。
- **避免全局可变状态**：配置/权重为不可变常量或显式传入；缓存走 Redis（ADR-004），不依赖模块级可变字典模拟缓存。
- **依赖注入**：外部服务（DB/Redis/LLM/数据源）通过接口注入，禁止在函数内直接 `import` 后硬编码连接。

### 1.6 并发与异步
- **CPU 密集**（评分/归因/批算）：用 `ProcessPoolExecutor` 跨进程（规避 GIL），禁止用多线程做重 CPU（见《详细设计》§2.22.1）。
- **I/O 密集**（LLM/HTTP/DB）：用 `asyncio`；LLM 调用必须 `asyncio.Semaphore(LLM_SEMAPHORE)` 限流（见 TP-02 §3.4.8），避免 429。
- **禁止**：在 `async` 函数中调用阻塞式同步 I/O（如 `requests.get`、同步 DB 驱动）且不 `await`；必须 `await` 或用线程池桥接。
- **分布式锁**：调度/采集等跨进程临界区用 Redis 锁（Redlock 思路），超时自动释放，防脑裂（见《详细设计》§3.14.6）。
- **无未来函数**：回测/评分严格按交易日时序，禁止用 `t` 日之后数据（详见 TP-04）。

### 1.7 依赖管理
- **锁定**：`requirements.lock`（pip-tools）或 `poetry.lock` 锁定全量版本；禁止 `latest` 浮动。
- **引入新依赖**：须经评审，且须有 fallback（见《详细设计》§2.15：AkShare 主源 + Tushare 备源 + 降级）；禁止引入与现有栈冲突的包。
- **导入**：显式导入，禁止 `from x import *`；标准库 / 第三方 / 本项目 三组导入分区空行隔开（isort）。

## 2. 目录规范

### 2.1 后端目录结构（推荐）
```
fund_invest/
├── api/                 # Web 入口(FastAPI/Flask)：路由、请求校验、依赖注入
│   ├── v1/
│   └── deps.py          # 鉴权/DB/Redis 依赖
├── domain/              # 领域与算法(纯逻辑, 不依赖 Web)：评分/归因/回测/宏观/筛选
│   ├── score/           # TP-01 评估引擎
│   ├── backtest/        # TP-04 回测
│   ├── diagnosis/       # TP-03 组合诊断
│   └── macro/           # TP-05 宏观底盘
├── schemas/             # Pydantic 请求/响应模型(§6.2 信封对齐 §2.21)
├── infra/               # 基础设施：db / redis / external(数据源/LLM) / lock
├── workers/             # 后台进程：采集 / 批算 / 周报(§3.14)
├── config/              # 配置加载(环境分离, §9.1)
├── tests/               # 单测/集成/e2e(§11 DoD)
└── scripts/             # 运维/迁移脚本(非业务代码)
```
- **单一归属**：同一能力只在一处实现；`domain/` 不被 `api/` 反向依赖。
- **配置即代码**：目录/模块命名稳定，禁止按人建目录。

### 2.2 前端目录结构（Streamlit，纯 Python）
```
app/
├── app.py                 # Streamlit 入口(仪表盘三段式 + 路由)
├── pages/                 # 多页(对应 12 页面原型, Streamlit 原生 pages)
│   ├── 01_仪表盘.py
│   ├── 02_数据中心.py
│   └── ...
├── components/            # 可复用 Python 组件模块(封装 st.xxx 复合控件)
│   ├── score_panel.py     # 五因子评分卡 + 因子分解条 + 滑杆
│   ├── brinson_chart.py
│   └── diagnosis_table.py # 红黄绿诊断表
├── state.py               # st.session_state 集中封装(组合/筛选条件/用户态)
├── api_client.py          # 统一请求封装(调 FastAPI 内部 API, 处理信封/错误码)
└── utils.py               # 纯函数(格式化/计算)
```
- **资源归属**：每个复合控件一个 `.py` 模块；页面级 `pages/*.py` 只做编排，重逻辑下沉到 `components/` 与 `domain/`；**不引入 TS/JS 前端工程**（与《详细设计》§2.7 一致）。

### 2.3 文档与配置目录
- 本项目交付文档统一置于 `基金评估系统_交付文档/`，新增规范归入 `11_开发规范/`。
- 环境配置（dev/test/prod）**禁止入库密钥**；用 `.env.example` 占位 + 密钥管理系统（§9.1）。

### 2.4 禁止项（红线）
- 禁止提交 `__pycache__/`、`.pytest_cache/`、`*.pyc`、`.env`、IDE 配置、大文件（>10MB 走对象存储）。
- 禁止在源码目录混入一次性脚本、数据 dump、评测产物（评测集归 `06_NL选基评测/`）。
- 禁止 `print()` 调试残留（改用 `logging`，见 §5）。

## 3. 文档规范

- **代码即文档**：公共模块 docstring 完整（§1.4）；复杂逻辑就近注释。
- **接口文档**：API 用 **OpenAPI 3** 自动生成（FastAPI 原生支持），禁止手写与代码脱节的接口文档；变更接口须同步 schema 与 `schemas/`。
- **设计文档版本化**：BRD/技术规格/详细设计/TP 文档带**版本号 + 日期**，变更须记录修订说明（参考既有文档头）。
- **架构决策记录（ADR）**：关键技术选型（如 ADR-001~004）写入 `docs/adr/`，含"背景/决策/后果/状态"，禁止无声决策。
- **README**：仓库根 README 含：项目简介、启动方式、环境要求、目录说明、常用命令、贡献指引。
- **CHANGELOG**：遵循 [Keep a Changelog](https://keepachangelog.com/)，按版本记录 Added/Changed/Fixed。
- **语言**：正文以**中文**为主，专业术语中英对照（如 回撤 drawdown、夏普 Sharpe），代码标识符英文。

## 4. 提交规范（Git）

### 4.1 分支模型（Trunk-Based 简化）
- **长期分支**：`main`（受保护，对应可发布状态）、`develop`（集成）。
- **临时分支**：`feature/<需求ID>-<简述>`（如 `feature/FR-19-dca`）、`fix/<问题>`、`hotfix/<版本>`。
- **保护规则**：`main` 禁止直接 push；须 PR + ≥1 评审 + CI 全绿方可合并；合并后删临时分支。

### 4.2 提交信息（Conventional Commits）
格式：`<type>(<scope>): <subject>`（中文 subject 允许，type 用英文）

| type | 含义 | 示例 |
|------|------|------|
| feat | 新功能 | `feat(score): 新增 Brinson 几何链接` |
| fix | 缺陷修复 | `fix(backtest): 修复分红双重计(E3)` |
| docs | 文档 | `docs(standards): 新增开发规范 v1.0` |
| refactor | 重构 | `refactor(nl): 规则兜底抽取` |
| perf | 性能 | `perf(score): 批算改多进程` |
| test | 测试 | `test(diagnosis): 补风险测评联动用例` |
| chore | 构建/杂项 | `chore(ci): 加 mypy 门禁` |
| style | 格式 | `style: black 格式化` |

- **subject**：祈使句、≤ 50 字、不以句号结尾；说明**做了什么/为什么**（关联需求：`关联 FR-19 / 闭合 E3`）。
- **body（可选）**：长说明、动机、影响面；**footer** 写 `BREAKING CHANGE:` 或 `Closes #123`。
- 禁止 `update`、`fix bug`、`temp` 等无意义信息。

### 4.3 Pull Request 规范
- **小步提交**：单 PR 聚焦一个需求/缺陷；禁止"巨无霸 PR"（>800 行需拆分或说明）。
- **必填信息**：需求/缺陷 ID、变更摘要、自测证据（单测通过/截图/评测报告）、风险评估。
- **评审**：≥1 人 approve；评审须覆盖逻辑/安全/性能/规范（§11 DoD）；评论须逐条解决。
- **CI 门禁**：lint + type + test + 覆盖率 + 构建，任一红**阻断合并**。

### 4.4 版本与标签
- 发布按 **SemVer**（`MAJOR.MINOR.PATCH`）；里程碑打 `git tag vX.Y.Z` 并写 CHANGELOG。
- 破坏性变更须 `BREAKING CHANGE` 标注并评审。

## 5. 日志规范

### 5.1 级别约定
`DEBUG < INFO < WARNING < ERROR < CRITICAL`；**生产默认 INFO**（DEBUG 仅排查时开）；ERROR 须有对应告警。

### 5.2 结构化日志（JSON）
统一用 JSON 结构，便于采集与检索。必含字段：
```json
{"ts":"2025-07-28T10:00:00Z","level":"INFO","service":"score","trace_id":"a1b2","user_id":"u1","action":"score_one","msg":"ok","cost_ms":120}
```
- `trace_id`：全链路贯穿（请求→计算→DB），用于跨服务排查（§6.2 / §4.2 信封 `trace_id` 同源）。
- `action`：动作标识（如 `dca_backtest`、`portfolio_diagnose`）。

### 5.3 敏感信息脱敏（红线）
- **禁止**记录密码、token、API Key、完整证件号、银行卡号、会话凭证原文。
- 用户标识用 `hash(user_id)` 或脱敏展示；PII 不入本地日志文件。
- 外部依赖返回的原始密钥在日志中 masking。

### 5.4 落盘与轮转
- 按**时间（天）+ 大小**切分（`TimedRotatingFileHandler` / logrotate），单文件 ≤ 100MB，保留 ≤ 30 天（合规要求另议）。
- 容器环境输出到 stdout/stderr，由采集层统一收集；禁止依赖本地磁盘持久化关键日志。
- 不在热路径（评分循环内）做重 I/O 日志；高频可采样。

### 5.5 异常日志
- 捕获异常须 `logger.exception(...)` 记录堆栈（含 `trace_id`）；禁止空 `except` 静默吞掉（§8）。

## 6. API 接口规范

### 6.1 RESTful 约定
- **资源名词复数**、小写：`/api/v1/funds`、`/api/v1/portfolios`；子资源 `/api/v1/portfolios/{id}/backtest`。
- **版本前缀** `/api/v1`；破坏性变更升 `v2`。
- **HTTP 动词语义**：GET 查询、POST 创建/动作、PUT 全量更新、PATCH 局部、DELETE 删除；**GET 必须幂等且无副作用**。
- **状态码**：2xx 成功、4xx 客户端、5xx 服务端；不在 200 体里藏错误（错误走 §7 信封 `code≠0`）。

### 6.2 统一响应信封（对齐《详细设计》§2.21）
```json
{"code": 0, "message": "ok", "data": {...}, "source": "batch", "as_of": "2025-07-28", "disclaimer": "仅供参考，不构成投资建议", "trace_id": "a1b2"}
```
- 成功 `code=0`；失败 `code≠0` 且 `data=null`（见 §7.3）。
- `source`：数据来源（`batch` 批算 / `realtime` 实时 / `cache` 缓存），用于溯源与降级标识。
- `as_of`：数据截至日期（金融数据强时效，必须带）。
- `trace_id`：与日志（§5.2）、错误（§7.3）同源，便于端到端排查。

### 6.3 命名与字段
- 字段 **snake_case**；时间 **ISO 8601 UTC**（如 `2025-07-28T10:00:00Z`）。
- **分页**：`?page=1&page_size=20`，响应含 `total` / `page` / `page_size`；大数据走游标（`cursor`）。
- **排序/过滤**：统一 `?sort=composite:desc&filter=risk<=15`，避免散落自定义参数。
- **大数/精度**：金额用整数分或字符串，避免浮点误差；NAV 等保留约定小数位。

### 6.4 鉴权与权限
- 用户接口用 **Bearer JWT**；`/api/admin/*` 需管理员态。
- 错误映射（见 §4.2 / §7.2）：未登录 `40101`、无权限 `40103`、守卫拦截 `40301`。
- 权限校验在**依赖注入层**统一做，禁止在业务函数里散落 `if not is_admin`。

### 6.5 限流
- 全局 + 单用户限流（令牌桶）；超限返回 **HTTP 429** + 错误码 `42901` + `Retry-After` 头（对齐 §4.2）。
- LLM 类接口额外受 `LLM_SEMAPHORE` 约束（§1.6）。

### 6.6 SLA（对齐《详细设计》§4.3）
- API P95：普通查询 ≤ 800ms，评估/筛选 ≤ 2s；错误率 < 1%；单实例 QPS ≥ 20。
- 监控阈值见 §2.16；超标告警；缓存命中率 ≥ 80%（热键 dashboard/top10/score）。

## 7. 错误处理

### 7.1 错误分类
- **客户端错误（4xx）**：参数/权限/业务规则，可预期，用户可修正。
- **服务端错误（5xx）**：内部计算/依赖异常，须告警与降级。
- **外部依赖错误**：数据源/LLM/DB 不可用，按 §2.15 降级。

### 7.2 错误码体系（对齐《详细设计》§4.2）
统一区间划分，新增错误码须在此体系内扩段，禁止随意数字：

| 区间 | 类别 | 示例 |
|------|------|------|
| `0` | 成功 | — |
| `400xx` | 参数/业务 | `40001` 参数校验失败、`40002` 资源不存在、`40003` 业务规则冲突 |
| `401xx` | 认证/权限 | `40101` 未认证、`40103` 无权限 |
| `403xx` | 守卫拦截 | `40301` 口径未定义被 `RESEARCH_PROXY_GUARD` 拦 |
| `429xx` | 限流 | `42901` 外部限频 |
| `500xx` | 内部异常 | `50001` 内部计算异常（已降级） |
| `503xx` | 依赖不可用 | `50301` 数据源、`50302` DB、`50303` LLM 超时降级 |

### 7.3 错误响应
- 统一信封（§6.2），失败体：`{"code":40001,"message":"参数校验失败: amount 必填","data":null,"source":null,"as_of":null,"disclaimer":null,"trace_id":"a1b2"}`。
- `message` **面向用户可读**、不泄露内部实现（SQL/堆栈/路径）；内部细节仅入 ERROR 日志（§5.5）。
- 必带 `trace_id` 便于用户反馈时定位。

## 8. 异常处理

### 8.1 分层异常（禁止裸 Exception）
项目定义异常层次，业务代码抛具体异常而非 `Exception`：
```
AppError(BaseException)
├── BizError            # 业务规则(40003 等)
├── ParamError         # 参数(40001)
├── AuthError          # 认证权限(40101/40103)
├── GuardError         # 守卫(40301)
├── ExternalError      # 外部依赖(42901/503xx)，含 cause
└── InternalError      # 内部(50001)
```
- 底层（infra）捕获第三方异常并**包装**为上述项目异常，保留 `cause`（`raise InternalError(...) from e`）。
- 禁止 `except Exception: pass` 静默吞掉。

### 8.2 全局异常处理（FastAPI/Flask）
- 注册全局 `exception_handler`，将项目异常映射为 §7 错误码信封；未预期异常兜底为 `50001` 并记录 ERROR 日志（含 trace_id）。
- 同一异常**只记录一次**（避免中间件+handler 重复记）。
- 测试须覆盖：参数错→40001、未登录→40101、依赖断→50301。

### 8.3 不泄漏内部信息（红线）
- 生产环境响应**不含**堆栈、SQL、内部路径、第三方密钥；友好消息 + 内部日志。
- 调试信息（堆栈）仅在 `DEBUG` 级别且非生产环境返回。

### 8.4 事务与回滚
- DB 写操作须在**事务边界**内；部分失败整体回滚（atomic）。
- 批量写入（如 `upsert_scores`）要么全成功要么全失败，禁止半量脏数据。
- 缓存与 DB 不一致时以 DB 为准，缓存可失效重建（ADR-002 唯一权威源）。

### 8.5 外部依赖降级（对齐 §2.15）
- 任何外部调用须有超时 + fallback：AkShare 失→Tushare；LLM 失→规则摘要（`50303`）；DB 失→`50302` 前端降级静态说明。
- 降级须**可观测**（日志标 `degraded=true` + 原因），且不阻断核心查询。

## 9. 发布规范

### 9.1 环境与配置（Twelve-Factor）
- 环境：`dev` → `test` → `staging` → `prod`，**配置外部化**（环境变量/配置中心），禁止在代码中硬编码环境差异或密钥。
- 密钥走密钥管理（Vault/云 Secrets），`.env` 仅本地且**不入库**。
- 生产数据禁止用于 dev/test（脱敏或假数据）。

### 9.2 CI/CD 门禁
- **流水线阶段**：lint → type → test(单元+集成) → 覆盖率 → 构建镜像 → 部署 staging。
- **覆盖率门禁**：单测覆盖率 **≥ 80%**（对齐《详细设计》DoD），核心算法（评分/归因/回测）须更高；接口 100% 命中 §2.21 契约。
- **阻断**：任一阶段失败阻断合并/发布；安全扫描（依赖 CVE）纳入。

### 9.3 版本与变更管理
- 语义化版本（§4.4）；CHANGELOG 记录；发布须有**变更评审**（OQ 机制，见《详细设计》）。
- **数据库迁移**：用迁移工具（Alembic），脚本**可逆**（up/down）；先备份后执行；禁止手动改生产库。
- 接口变更须向后兼容或走新版本（`/api/v2`）。

### 9.4 灰度与回滚
- 发布采用**金丝雀/灰度**（先小流量），监控 P95/错误率/资源。
- **一键回滚**：保留上一稳定镜像与 tag；异常自动/手动回滚。
- 发布窗口避开交易时段（避免影响实时数据）。

### 9.5 发布检查清单（DoD 触发）
- [ ] 单测/集成全绿、覆盖率达标
- [ ] lint/type 零新增问题
- [ ] CHANGELOG/版本号更新
- [ ] 接口文档(OpenAPI)同步
- [ ] 监控/告警就绪
- [ ] 回滚方案明确
- [ ] 安全扫描无高危

## 10. 前端规范

### 10.1 框架与语言
- 前端采用 **Streamlit（纯 Python，1.35+）**，与后端同语言栈；**禁止另起 TS/JS 前端工程**（与《详细设计》§2.7、技术规格、可行性评估一致）。
- 强类型：Streamlit 脚本用 **pyright** 做类型检查（纳入 §1.3 类型体系）；关键数据模型复用 `domain/` 的 dataclass / TypedDict，禁止 `Any` 蔓延。
- 单一进程入口 `app.py`；多页用 Streamlit 原生 `pages/`；禁止混用多套前端构建。

### 10.2 组件与目录（§2.2）
- **单一职责**：每个复合控件（评分卡 / 归因图 / 诊断表）封装为一个 `components/` 下的 Python 函数，入参明确；页面级 `pages/*.py` 只做编排。
- **命名**：组件模块 `snake_case`，导出函数 `snake_case`；与 Streamlit 控件语义一致。
- **无巨组件**：单页脚本 > 200 行考虑下沉到 `components/`；跨页复用逻辑抽 `utils.py` / `state.py`。

### 10.3 状态管理
- 跨页/跨交互状态统一用 **`st.session_state`**，集中封装在 `state.py`（组合/筛选条件/用户态）；避免散落全局可变变量。
- 服务端数据（基金/评分）由 `api_client.py` 拉取并缓存；与后端缓存策略（§6.6 命中率）协同，前端不手动维护过期副本。

### 10.4 样式与主题
- 用**设计令牌**（CSS 变量 + `config.toml` + `static/style.css`）统一色板/间距/圆角，并作为**唯一权威源**；**涨跌幅语义全局唯一遵循"红涨绿跌"（A股惯例，对齐《原型设计说明》§5）**：正收益 = 红、负收益 = 绿，品牌翠绿仅作标识、不得用于涨跌表达；禁止散落魔法色值、禁止令牌外游离色与相反配色（R7 文档同步）。
- 响应式优先（Streamlit 默认响应式，自定义布局用 `st.columns` / `st.container`）；暗色模式与全局主题一致。
- 命名一致（CSS 变量集中管理，全项目统一）。

### 10.5 API 调用
- 统一请求封装在 `api_client.py`（requests / httpx 调 FastAPI 内部 API），**统一处理信封（§6.2）与错误码（§7.2）** → 全局提示 / 降级。
- 禁止硬编码完整 URL / Token（用配置或环境变量）；错误码 `40101/40103` 统一跳登录。
- 不在前端做鉴权信任判断（后端为准）。

### 10.6 性能
- **缓存优先**：重计算 / 数据获取用 `@st.cache_data`（按输入哈希）/ `@st.cache_resource`（连接 / 模型）；避免每次交互重跑整脚本。
- **局部刷新**：重交互区块用 `@st.fragment` 或 `st.session_state` 控制，避免整页重算；大数据表（持仓 / 榜单）分页或虚拟滚动。
- 输入（筛选/搜索）**防抖**（`on_change` + `session_state`）；资源 / 图片压缩；关注首屏与交互 P95（对齐 §6.6 SLA）。

### 10.7 可访问性（A11y）
- 语义标签、表单 label、`aria-*`；键盘可达；颜色对比度达标；图表提供文本替代。

### 10.8 安全（红线）
- **XSS**：禁止用 `st.markdown(unsafe_allow_html=True)` / `st.html()` 渲染**未净化的外部内容**（新闻标题 / 舆情须先 HTML 转义，见《详细设计》安全章节）；确需内联 HTML 须白名单净化（bleach）。
- **CSP**：如自定义 HTML 组件，配置内容安全策略；禁止注入内联脚本与外部不可信脚本。
- **输入校验双端**：前端校验体验，后端校验权威（§6.4/§7）。
- 禁止在前端硬编码密钥或做权限绕过。

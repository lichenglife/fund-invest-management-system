## 3. 分领域详细发现

### 3.1 产品 / 需求视角
- **正向**：模块↔需求映射表（§2.17）是本项目最扎实的可追溯性资产；回本测算、定投信号、T 日成交、分红复权等核心业务规则描述准确，与投顾方法论一致。
- **投资业务合理性（投顾视角）**：
  - 估值定投信号（<30%→1.5x，>70%→0.5x，>90%→停投）方向正确，但阈值偏"经验值"，应如诊断规则（OQ-14）一样**集中配置 + 导师审定**，避免硬编码误导。
  - PEG/ERP 代理口径带"(代理)"标注 + "相对高低提示，非绝对结论" + `RESEARCH_PROXY_GUARD` 守卫——**这是良好的风控设计**，杜绝 naive 计算误导用户，应予保留并测试覆盖。
  - Brinson 归因限定主动股混基（`BRINSON_SCOPE=["mixed","stock"]`），指数基改显跟踪误差/信息比率、债基不显——范围判定正确。
- **待补**：§3.4.7 称"基于 100 条标注评测集"，而当前已建成 **160 条回归语料（100 结构化 + 60 对抗）**，引用需同步更新，避免实现期误用旧基线。

### 3.2 开发 / 架构视角
- **正向**：模块化单体选型（ADR-001）与单人+AI Coding 现状匹配；评分唯一权威（ADR-002）有效防止跨模块评分漂移；三层存储（ADR-003）取舍合理。
- **关键缺口**：
  1. **数据模型缺 ER 图与 DDL（B2）**：各模块仅列表面级表名，未声明外键（`paper_positions→paper_accounts`、`scores→funds`、`holdings→funds` 等），3NF 未论证；开发建表无据，2.2 要求"字段设计与 ER 图一致"无法满足。
  2. **接口契约不完整（S-接口）**：端点已枚举，但**缺请求/响应字段 schema**（仅 §4.2 通用信封）。建议以 OpenAPI 补字段级契约，否则前后端联调与测试成本高。
  3. **接口命名不一致（B-接口）**：`/api/funds/{code}` vs `/api/fund/{code}` 混用，须统一为复数资源名。
  4. **事务边界未声明（S3）**：模拟交易买/卖须保证"现金−持仓−流水"原子；重置（`/reset`）与在跑回测（`/dca-backtest`）的竞态未定义。
  5. **算法公式精度不足（§3.3）**：Brinson 归因、五因子归一化（权重 30/25/20/15/10 如何合成综合分）缺数学表达；当前为流程级描述，编码易歧义。

### 3.3 质量控制 / 测试视角
- **正向**：核心逻辑与外部环境解耦（采集多源适配、domain 分层），Mock 友好；2.19.4 明确禁止"返回未标注默认数值"，利于异常测试断言。
- **关键缺口**：
  1. **无测试策略（S1）**：缺单元测试/集成测试覆盖重点章节；技术规格 v1.3 已提及 `test_research_proxy.py`/`test_screen.py`，详细设计未承接。
  2. **错误码规范缺失（S2）**：§4.2 仅 `code:0`，无失败码枚举；异常流（14.1）无测试方法设计，QA 无法构造断言。
  3. **性能指标目标缺失（13.2）**：§2.16 只有监控阈值（P95>2s 告警），无"设计目标 RT/QPS"，无法判定是否达标。
  4. **NL 准确率 SLA 可测**：`NL_ACCURACY_TARGET=0.85` 已有评测集支撑，可作为验收用例直接复用（优势项）。

### 3.4 运维视角
- **正向**：备份策略完整（§2.14 日备 + 月演练）、容错表 2.15 覆盖主要故障、监控指标 2.16 齐备、第三方 SLA+降级明确（§2.9）。
- **待补**：平滑发布（16.1）、一键回滚（16.2，仅 Alembic 隐含 downgrade）、多环境配置（17.1）未显式定义；日志级别/结构化（15.1）未规范。

### 3.5 安全视角
- **正向**：密钥外置、XSS 受控（Streamlit + 转义）、AI 输出强制"仅供参考，不构成建议"、敏感计算降级不臆测。
- **关键缺口（S3）**：**`/api/admin/trigger-job`（§3.14.4）无任何鉴权**——即使单用户 MVP 部署在内网，手动触发采集/重算/备份属高风险操作，至少应加来源 IP/本地网络限制或最小令牌；需产品与安全书面确认风险接受。

## 6. 整改优先级与开工建议

1. **开工前（必改，阻塞级）**：B1 版本对齐、B2 补 ER/DDL。预计 1–2 天文档补强。
2. **Phase 1 开发并行补强（严重级）**：S1–S5 随模块实现同步补齐（接口 schema、错误码、事务边界、算法公式、测试策略）。
3. **Phase 2+ 演进（建议级）**：A1–A8 纳入后续迭代，其中熔断/限流/回滚（A2/A4）建议在接入公网或多人使用前完成。

> **总体评价**：本详细设计说明书架构清晰、模块映射扎实、风控与降级意识到位（PEG/ERP 守卫、AI 免责、异常不臆测均为亮点），具备进入 MVP 开发的主体条件。主要短板集中在**数据模型形式化（ER/DDL）、接口契约精度、测试与错误码规范、管理端点鉴权**四类工程化细节，均可在开工前/提测前闭环，不构成方向上的返工风险。

# 基金评估与模拟交易系统 · 需求变更管理规范（Change Management）

> **版本**：v1.0 ｜ **适用范围**：本项目**开发阶段**全部需求活动（新增 / 修改 / 删除），凡涉及现有**技术设计、数据库、接口契约、金融算法口径、范围边界**的改动均须遵循本规范。
> **目的**：在已进入编码（Phase 1）的前提下，规范"需求不满足 → 重新分析 / 设计 / 改库"等活动的提出、评审、实现与关闭，保证交付质量、可追溯性与可回滚。
> **性质**：强制性流程规范（硬约束 R1–R8 违反即拦截合并 / 发布）；与《开发规范(v1.0)》《详细设计(v1.1)》《技术方案(TP-01~06)》《开发任务分解(v1.1)》《CLAUDE.md》共同构成编码期强制依据。

---

## 0. 为什么需要本规范

开发阶段最容易出现的质量塌方不是"写不出代码"，而是**无管控的变更**：

- 开发者自行"优化"算法口径，导致 E1–E14 已闭环的金融正确性被悄悄回退；
- 需求不满足时直接改库表 / 删字段，未走迁移，生产不可回滚；
- 接口加字段破坏存量前端契约，或静默删除已规划需求无人知晓；
- 代码与文档脱节——实现变了，详细设计 / TP / 错误码体系没同步。

本规范用**分级 + 标准流程 + 硬约束**三件套，把"改什么、谁定、怎么改、能否回退、是否留痕"固化下来。

> **一致性优先级**：本规范与《详细设计》《开发规范》《技术方案(TP)》冲突时，以**详细设计 + 开发规范 + 对应 TP** 为准；涉及算法口径以对应 TP 文档为准。本规范不取代 ADR（技术选型类变更仍须写 ADR，`docs/adr/`）。

---

## 1. 变更分级（C1 / C2 / C3）

任何变更先定级，再走对应流程。**定级存疑时按就高不就低**。

| 级别 | 名称 | 典型范围 | 审批人 | 是否强制登记 CR |
|------|------|----------|--------|------------------|
| **C1** | 轻量（local） | 内部实现细节（不改公开契约）；纯重构（行为不变）；注释 / 文档修正；单测补充；局部变量 / 日志调整 | 开发者自评 + 技术 Lead 知晓 | 建议登记（CHANGELOG 一笔即可） |
| **C2** | 中度（minor） | 接口**向后兼容**字段新增；新增内部模块 / 函数；配置参数调整；新依赖引入（须评审 + fallback）；非破坏性算法实现优化（不触动 E1–E14 口径） | 技术 Lead 审批（PR ≥ 1 评审） | **必须登记** |
| **C3** | 重度（major） | 偏离现有设计 / 架构；**数据库 schema 变更**（建表 / 改字段 / 删表）；**接口破坏性变更**；**金融算法口径变更**（E1–E14 相关）；**删除需求 / 删除表 / 删除字段**；范围新增（计划外功能） | 架构 + 产品 + 技术**联合评审**（涉及选型须补 ADR） | **必须登记 + 影响分析** |

**判定辅助**：
- 触及 `domain/score / brinson / backtest / diagnosis / macro` 等核心算法且改变计算口径 → 至少 C2，涉及 E1–E14 闭环项 → **C3**。
- 触及 `schemas/`、`migrations/`、`api/` 路由签名 → 至少 C2；删除 / 破坏性 → **C3**。
- 改动与《详细设计》《技术规格》《TP》描述不一致，且文档未先更新 → **C3（先改文档，再实现）**。

## 2. 标准流程（7 步）

```
① 提出 ──→ ② 影响分析 ──→ ③ 评审决策 ──→ ④ 设计修订 ──→ ⑤ 实现 ──→ ⑥ 验证 ──→ ⑦ 关闭
  (CR)        (Impact)        (Review)        (Design)       (Impl)      (Verify)      (Close)
```

### ① 提出（Open）
- 提交 **Change Request（CR）**，填写 §4 模板；一个 CR 聚焦**一类**变更（禁止"大杂烩 CR"）。
- CR ID 规则：`CR-<YYYYMMDD>-<序号>`（如 `CR-20250729-01`），写入标题与分支名。
- 触发场景：需求不满足、评审发现设计缺陷、线上问题需改设计、范围蔓延、依赖 / 环境变化。

### ② 影响分析（Impact Analysis）
- C2 / C3 **必须**填写 §5《影响分析模板》，至少覆盖：**设计 / 数据库 / 接口 / 算法口径 / 文档 / 测试 / 回滚** 七维度。
- 明确"是否触动 E1–E14""是否触动 ADR-001~004""是否需 Alembic 迁移""是否影响现有前端契约"。
- 影响分析是评审决策的**输入依据**，未分析不得进入评审。

### ③ 评审决策（Review & Decide）
- 按 §1 分级确定评审人；评审须给出 **Approve / Reject / Revise** 结论，并注明约束（如"仅允许向后兼容"）。
- C3 须留评审记录（PR 评论 / 会议结论 / ADR），结论写入 CR 与 CHANGELOG。
- 评审**不通过**则回到 ① 或关闭（Reject 须写理由）。

### ④ 设计修订（Design Revision）
- 先改文档、后改代码：**更新对应文档**（详细设计 / 技术规格 / TP / 错误码体系），登记 **ADR**（若涉及技术选型），在 **CHANGELOG** 记 Added/Changed/Fixed。
- 数据库变更：**先写 Alembic 迁移草案**（up/down 可逆），不手写 DDL。
- 文档修订须带版本号 + 日期 + 修订说明（同《开发规范》§3）。

### ⑤ 实现（Implement）
- 分支：`feature/<cr-id>-<简述>`（C3）/ `fix/<cr-id>-<简述>`（修复型），遵循《开发规范》§4 分支模型。
- 提交信息 Conventional Commits 且 footer 关联：`Closes CR-20250729-01`；金融口径变更须注明 `闭合/保持 E1–E14`。
- 库变更只走 Alembic（`migrations/`），禁手写 DDL（R3）。

### ⑥ 验证（Verify）
- 单元 / 集成测试全绿，覆盖率 ≥ 80%（核心算法更高），接口 100% 命中 §2.21 契约。
- **金融口径回归**：E1–E14 相关变更须跑对应 TP 的 test oracle / 评测集，证明未回退。
- 迁移验证：在 staging 执行 up 后执行 down，确认可回滚（R3 / R8）。

### ⑦ 关闭（Close）
- PR 合并（`main` 受保护，≥ 1 评审 + CI 全绿）；CR 状态置 **Closed**，CHANGELOG 标注版本 / tag。
- 归档：CR 模板、影响分析、评审结论、关联 commit/PR 一并留痕（R8）。
- 若变更延期 / 部分落地，按《DEFERRED.md》登记（D 编号），不静默丢弃。

## 3. 硬约束（R1–R8，违反即拦截合并 / 发布）

> 下列约束为**红线**，CI / 评审 / 发布门禁均须检查；违反须拦截，不得"先合后补"（紧急通道见 §7）。

- **R1 禁止偏离设计**：所有实现须有对应权威文档依据（BRD / 技术规格 / 详细设计 / TP）。**任何超出引用文档的设计 / 库表 / 接口改动，必须先在 CHANGELOG 登记 CR 并经评审，禁止自行变更。**
- **R2 金融红线不可退**：E1–E14 已闭环项**禁止回退**；任何变更须保证不破坏 Brinson 真实权重 + OTHER_CASH 残差 + 几何链接、五因子 `ret/risk/perf/scale/manager` 口径、后复权净值、全收益基准、诊断阈值联动 `risk_type`、ERP 拆大/小盘(7:3) 等闭环结论。
- **R3 库变更走 Alembic 可回滚**：禁止手写 DDL；所有 schema 变更经 `migrations/`（Alembic），脚本 **up/down 可逆**；执行前先备份，staging 验证 down 可回滚。
- **R4 删除最严**：删除表 / 字段 / 接口须 **C3 + 数据迁移 / 双写兼容期**；禁止硬删生产数据（软删 / 改名过渡优先）。
- **R5 接口稳定**：接口变更须**向后兼容**或走新版本（`/api/v2`）；破坏性变更须评审 + 版本化 + 兼容期；错误码在 §7.2 体系内扩段，禁止随意数字。
- **R6 删除需求纪律**：删除已交付 / 规划中需求须记录**理由 + 影响 + 替代方案**，禁止静默删除；被删需求在文档与 CHANGELOG 标注，不凭空消失。
- **R7 文档同步强制**：设计 / 数据库 / 接口 / 算法变更须**同步更新对应文档**（CHANGELOG / 详细设计 / TP / ADR / 错误码体系），禁止代码与文档脱节；OpenAPI 随 schema 自动更新。
- **R8 可追溯回滚**：每个 CR 关联 commit / PR / 文档修订 / 迁移版本；保留回滚路径（镜像 tag + 迁移 down），确保任意变更可定位、可撤销。

## 4. Change Request（CR）模板

```markdown
# CR-<YYYYMMDD>-<序号> · <一句话标题>

- 提出人：<name> ｜ 提出日期：<YYYY-MM-DD> ｜ 状态：Open / In-Review / Approved / Rejected / Closed
- 级别：C1 / C2 / C3
- 触发来源：需求不满足 / 评审缺陷 / 线上问题 / 范围蔓延 / 依赖变化

## 1. 背景与动机
（为什么需要这次变更？现状痛点 / 需求缺口 / 设计矛盾）

## 2. 变更内容
- 新增：<…>
- 修改：<…>（含前后对照）
- 删除：<…>（须说明替代 / 兼容）

## 3. 影响面（概要）
设计 / 数据库 / 接口 / 算法口径(E1–E14) / 文档 / 测试 / 回滚
→ 详见《影响分析》（C2/C3 必填，见 §5）

## 4. 评审结论
- 评审人：<…> ｜ 结论：Approve / Reject / Revise
- 约束：<…>（如"仅允许向后兼容""须补 ADR-00X"）

## 5. 落地与关闭
- 关联分支 / PR：<…>
- 关联 commit：<…>
- CHANGELOG 版本 / tag：<…>
- 关闭日期：<…>
```

## 6. 与现有体系衔接

| 既有机制 | 在本规范中的角色 |
|----------|------------------|
| **ADR-001~004**（模块化单体 / 评估引擎唯一权威源 / 三层存储 / Redis 多副本） | 涉及架构 / 存储选型变更须补 ADR，本规范不替代 ADR 流程 |
| **E1–E14（金融正确性闭环）** | 口径相关变更触发 R2，须跑 TP test oracle 证明未回退 |
| **DEFERRED.md（D1–D5）** | 变更若延期 / 部分落地，按 DEFERRED 登记 D 编号，不静默丢弃 |
| **DoD（合并 / 发布）** | 变更实现的"验证"步骤（⑥）以 DoD 为最低门槛（覆盖率 ≥ 80%、接口 100% 命中 §2.21） |
| **Conventional Commits / PR 门禁** | 实现步骤（⑤）强制关联 CR ID，PR ≥ 1 评审 + CI 全绿 |
| **Alembic 迁移** | 库变更唯一通道（R3），禁手写 DDL，up/down 可逆 |
| **统一响应信封 / 错误码体系** | 接口变更须保持信封 7 字段、错误码在 §7.2 区间扩段（R5） |
| **CHANGELOG（Keep a Changelog）** | CR 台账与关闭留痕（R7 / R8），见根目录 `CHANGELOG.md` |

## 7. 例外与紧急通道

- **生产事故 / 安全漏洞（hotfix）**：允许先分支 `hotfix/<版本>` 修复并合并，**事后 24h 内补登 CR**（标注"紧急通道"），不得借紧急之名长期绕开评审。
- **C1 局部修正**：开发者自评即可，仍建议在 CHANGELOG 记一笔（Added/Changed/Fixed），保持台账连续。
- **禁止项**：不得以"紧急""来不及"为由违反 R2（金融红线）、R3（库不可回滚）、R4（硬删生产数据）——这三类无例外。

## 8. 登记台账（CHANGELOG.md 结构）

根目录 `CHANGELOG.md` 遵循 [Keep a Changelog](https://keepachangelog.com/)，按版本记录。变更管理规范自身作为首个登记项：

```markdown
## [Unreleased]
### Added
- 需求变更管理规范 v1.0（13_需求变更管理规范）：变更分级 C1/C2/C3、7 步标准流程、硬约束 R1–R8、CR / 影响分析模板（CR-20250729-01）

### Changed
- 开发规范 v1.0 新增 §13 变更管理 / 变更红线（引用本规范 R1–R8）
- CLAUDE.md §1 硬约束新增第 6 条：超引用文档的改动须先登记 CR 并评审（R1）
```

> 每个 CR 关闭时，将其实质改动归并到对应版本段（Added / Changed / Fixed / Removed）；删除类变更记入 `Removed` 段并附理由（R6）。
